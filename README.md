# two-man-dev

Claude Code 2セッションによる軽量ペアプログラミングツール。

## これは何か

Claude Codeを「実装担当(diver)」と「相談役(operator)」の2セッションに分けて、tmuxの2ペインで同時に動かす。ユーザーがペインを切り替えながら両方と直接会話する、シンプルなツール。

diverはコードを書く。operatorは設計方針とレビューを出す。ユーザーは両方と話しながら開発を進める。

仕組みはシンプルで、tmux（または cmux）+ 起動スクリプト + 通信スクリプト1本で成立する。

## 背景: Claude Code 1セッションの限界

Claude Codeは1セッションでも十分強力だが、ある程度の規模の開発になると限界が出てくる。

**実装と設計相談が混ざる問題。** 1セッションで実装しながら設計相談もすると、コンテキストが汚れる。「やっぱりこの方針で」「いや戻そう」という試行錯誤がセッションに残り、コンパクション後に意図が失われやすい。

**かといってマルチエージェントは大げさ。** タスク管理やオーケストレーションの仕組みを介すと、「この既存メソッドを使うべき」のような暗黙の設計意図が中間層で劣化する。並列作業には強いが、ユーザーの目が必要な作業では確認待ちがボトルネックになり、結局1件ずつ対話した方が速いことがある。

two-man-devはこの中間にある: **1セッションでは足りないが、マルチエージェントほどの仕組みは要らない**、という場面のためのツール。

## 設計思想

- **ユーザーが両方のエージェントと直接会話する。** 情報の中間層がなく、意図がそのまま伝わる
- **diverとoperatorは対等。** operatorの提案は命令ではなく、diverは反論してよい
- **ユーザーがオーケストレーター。** ユーザーが離席すれば止まる。自分の目で見て判断したい場面向き

## 誰向きか

- **自分で全部の行動を見たいが、AIに相談しながら決めたい人。** 実装の判断をAIに丸投げしたくないが、壁打ち相手は欲しい
- **実装しながら設計相談を並行して進めたい人。** コードを書く手は止めず、隣のペインで「この設計どう思う？」と聞きたい
- **実装者視点と俯瞰視点の両方が欲しい人。** 実装しているからこそ見えること、外から見ているからこそ見えることがある

逆に、こういう人には向かない:

- ゴールが明確で、すぐAIに指示を出せる → 1セッションで十分
- AIに完全お任せで並列に回したい → マルチエージェントの方が向いている

## 前提

- macOS / Linux
- tmux または [cmux](https://cmux.dev)（cmux 使用時は tmux 不要）
- Claude Code (`claude` コマンドが PATH に通っていること)

## セットアップ

```bash
git clone <this-repo> ~/tools/two-man-dev
chmod +x ~/tools/two-man-dev/start.sh ~/tools/two-man-dev/start-cmux.sh ~/tools/two-man-dev/send.sh
```

## 使い方

```bash
# プロジェクトディレクトリを指定して起動
~/tools/two-man-dev/start.sh ~/path/to/project

# 省略時はカレントディレクトリ
~/tools/two-man-dev/start.sh

# セッション名を指定して起動（同一プロジェクトで複数セッション起動時）
~/tools/two-man-dev/start.sh -n feature-auth ~/path/to/project
# → tmuxセッション名: two-man-feature-auth
```

`-n` を省略した場合、セッション名はプロジェクトディレクトリ名から自動生成される（例: `two-man-myproject`）。

起動すると tmux セッションが作られ、左ペイン(diver)・右ペイン(operator) にそれぞれ Claude Code が起動する。各エージェントは自動で役割ファイルを読み込む。

- **左ペイン (0.0)**: diver - 実装担当。コードを書く
- **右ペイン (0.1)**: operator - 相談役。設計・レビュー・方針提案

ユーザーは tmux のペイン切り替え (`Ctrl-b` + 矢印キー) で両方と直接会話する。



### cmux を使う場合

tmux の代わりに cmux を使う場合は、start-cmux.sh / resume-cmux.sh を使う。

```bash
# cmux ネイティブで起動（tmux 不要）
~/tools/two-man-dev/start-cmux.sh ~/path/to/project

# セッション名を指定
~/tools/two-man-dev/start-cmux.sh -n feature-auth ~/path/to/project

# resume
~/tools/two-man-dev/resume-cmux.sh -n feature-auth -d "feature-auth diver" -o "feature-auth operator" ~/path/to/project
```

cmux 版では、tmux セッションの代わりに cmux ワークスペース + ペイン分割でセッションを構成する。send.sh は環境を自動検出して cmux / tmux どちらでも動作する。

### 典型的なフロー

```
1. diver に初期実装を指示
2. diver が実装完了 → operator にコードレビュー依頼を送信
3. operator がレビューし、修正指示を diver に送信
4. diver が修正（ここまでユーザーの手を介さず1往復が回る）
5. ユーザーが確認。必要なら operator に相談して方針を詰める
6. 繰り返し
```

ポイントは **2→3→4** の流れで、初期実装後のコードレビュー1往復をエージェント間で自動的に回せること。指示の出し方次第で、ユーザーが確認する頃にはレビュー済みのコードが出来上がっている。

途中で方針を変えたいときは、operatorに相談して結論を diver 向けの修正指示にまとめてもらい、`send.sh` で送ってもらえばいい。ユーザーが「operatorの出力をコピーしてdiverに貼り付ける」必要がない。

AIを複数セッション立てて開発したことがある人なら、ウィンドウ間のコピペの煩わしさを経験しているはず。`send.sh` がこれを解消する。簡単なやり取りならエージェント同士で自律的にやりとりできるし、大きな方針判断が必要なときはユーザーが間に立てばよい。

### エージェント間通信

エージェント同士は `send.sh` で連絡を取る。ユーザーが使う必要はない。

```bash
# diver → operator: 設計相談
bash /path/to/send.sh operator "この設計で問題ないか確認してほしい"

# operator → diver: 相談結果を修正指示として送信
bash /path/to/send.sh diver "既存の foobar メソッドを使う方式に変更してほしい。理由は..."
```

送信元は自動でプレフィックス (`[from: diver]` / `[from: operator]`) が付与される。

## ファイル構成

```
two-man-dev/
  start.sh       - tmux版: セッション起動 + Claude Code起動 + 役割自動読み込み
  start-cmux.sh  - cmux版: 同上（tmux不要）
  resume.sh      - tmux版: セッション resume
  resume-cmux.sh - cmux版: 同上（tmux不要）
  send.sh        - エージェント間通信（tmux/cmux 自動判定）
  diver.md       - diver の役割定義
  operator.md    - operator の役割定義
```

## カスタマイズ

`diver.md` / `operator.md` を編集すれば役割の振る舞いを変更できる。ファイル内容はセッション起動時に Claude が読み込む。

## 実際の使用例

以下は、あるRailsプロジェクトで機能を開発した際の実際のやりとりから抜粋して少し内容をぼかしたもの。

---

### 例1: operatorと設計を議論 →「diverに伝えて」で完結

ユーザーがoperatorに設計の相談をして、結論をdiverに伝達させる流れ。

```
[ユーザー → operator]
  既存の set_items メソッドの命名って、現状のままで適切ですか？
  ページネーション付きの一覧取得に使われているのに、名前にそのニュアンスがない。
  フラットに考えると set_items_page にリネームした方が良いのでは？

[operator]
  おっしゃる通り、set_items が一番汎用的な名前なのにページネーション専用なのは
  不自然ですね。ただ、今回のスコープでリファクタリングの範囲を広げすぎない方が
  安全という判断もあります。
  別PRでリファクタリングとして切り出す手もありますが、どうしますか？

[ユーザー → operator]
  リファクタリングを別にやる時間は基本的にないので、
  関連箇所をいじる今がチャンスだと思います。フラットに考えるとどう思いますか？

[operator]
  フラットに考えると、今回やる方がよいと思います。
  - ここでやらないと set_items がページネーション付きメソッドの名前として定着する
  - 今回まさに set_items を分解したので、命名を整理するのに最も自然なタイミング
  - 影響範囲は index アクション内の1箇所だけ

[ユーザー → operator]
  ありがとうございます。diverに伝えてもらえますか？
  反論が来るかもしれませんが、その時はあなたが納得した理論で伝え直してください。

[operator → diver (send.sh経由)]
  命名のリファクタリング提案です。現在の set_items はページネーション付きの
  index 専用メソッドですが、名前にそのニュアンスがありません。
  set_items → set_items_page にリネームしませんか。
  今回 set_items を分解したタイミングだからこそ整理するチャンスです。
```

**ポイント**: operatorは最初「現状維持でよい」と回答したが、ユーザーが「後方互換を気にしすぎでは」と押し返し、operatorが考えを改める。結論が出たら「diverに伝えて、反論が来たら対応して」で委任。設計の壁打ち→結論の伝達→反論対応の委任がコピペなしで完結する。

---

### 例2: diverが実装中に技術的制約を発見 → operatorと解決

operatorが出した方針がフレームワークの制約で実現不可能だった場合に、diverが代替案を提示して解決する流れ。

```
[operator → diver (send.sh経由)]
  ステータスラベルの定義ですが、i18n のキーを status_for_export に変更して、
  _i18n メソッドで取得する方式にしてください。

[diver → operator (send.sh経由)]
  確認です。enum_help の _i18n メソッドは実際の enum 定義に対して自動生成されるため、
  status_for_export という enum は存在せず、status_for_export_i18n メソッドは
  使えません。対応方法として2つ考えられます:
  (A) I18n.t で直接参照する
  (B) キーは既存の status のまま使い、将来の移行時に対応する
  いかがでしょうか？

[operator → diver (send.sh経由)]
  指摘はその通りですね。(A) の I18n.t で直接参照する方式でお願いします。
  エクスポート専用のラベルなので、enum_help の自動生成に乗せる必要はありません。
```

**ポイント**: operatorの設計意図とdiverの実装知識がぶつかり、より良い解に到達している。diverはoperatorの指示を鵜呑みにせず、技術的制約に基づいて反論する。operatorはそれを認めた上で判断を返す。1セッションでは自分自身に反論する形になるが、2セッションなら自然に議論が成立する。

---

### 例3: diver実装完了 → operatorが自動レビュー

ユーザーが介入せずに、エージェント間でコードレビューの1往復が回る流れ。

```
[diver → operator (send.sh経由)]
  /tmp/two-man-dev-review-request.md を読んでください。
  CSVエクスポート機能の実装が完了しました。
  全テスト通過（2000 examples, 0 failures）、Lintクリーンです。
  一次レビューをお願いします。差分の確認方法はファイル内に記載しています。

  --- operatorがdiffを読み、コードをレビュー ---

[operator → diver (send.sh経由)]
  /tmp/two-man-dev-review-result.md を読んでください。一次レビュー結果です。
  （4件の指摘: nilガード追加、ステータスラベルの不整合、
    eager loading の確認、テストケースの追加提案）
```

**ポイント**: diverが実装を終えると、ユーザーの手を介さずoperatorにレビューを依頼し、operatorがdiffを読んでレビュー結果を返す。ユーザーが確認する頃にはレビュー済みのコードが出来上がっている。

---

### 例4: operatorが出力データを確認 → 問題を切り分けてdiverに修正指示

operatorがエクスポートされたデータを確認し、問題の切り分けまで行う流れ。

```
[ユーザー → operator]
  出力されたCSVファイルを確認してもらえますか？何か気になる点があれば教えてください。
  /path/to/exported_data.csv

[operator]
  確認しました。5点気になる箇所があります。
  1. 支払方法欄に不完全な表示がある行がある（関連レコードがnil）
  2. 郵便番号に「〒150--0001」とハイフンが重複している行がある
  3. ...

[ユーザー → operator]
  開発環境のデータが不完全な可能性もありますよね。
  本番で起きうるものかどうか、調査してもらえますか？

  --- operatorがコードベースを調査 ---

[operator]
  調査しました。
  1. 関連レコードnil → 本番で起きうる。レコード削除後のケース。修正必要。
  2. 郵便番号ハイフン重複 → 開発データの問題。バリデーションで7桁必須のため本番では
     起きない。対応不要。
  diverに修正が必要な1件を伝えますか？

[ユーザー → operator]
  お願いします。

[operator → diver (send.sh経由)]
  CSVの支払方法欄について修正依頼です。関連レコードが nil の場合に
  不完全な文字列が表示されます。nilガードを追加してください。
```

**ポイント**: operatorが実データの確認→原因調査→本番影響の判断→修正指示の作成まで一貫して行う。ユーザーは「調べて」「伝えて」だけで、調査結果と判断をoperatorに任せられる。
